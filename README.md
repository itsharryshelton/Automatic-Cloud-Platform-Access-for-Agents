# Automatic Cloud Platform Access for Agents

Per-folder cloud logins for Azure (`az`), Cloudflare (`cf`, `wrangler`) and the GitHub CLI (`gh`) on Windows.

`cd` into a customer folder and the right credentials switch in automatically; leave it and they switch back. AI agents (Claude Code, T3 Code) get the same credentials through a one-line prefix, and a guard hook stops them making cloud changes that should go through a pipeline.

> [!WARNING]
> This is just a way I found that works for multiple customer access across repos/folders; I am not claiming this to be the best way or the most secure way, the secrets are encrypted when used properly. Use your own judgement :)
>
> This is designed for Windows without needing WSL methods; and designed when a sandbox per repo/customer isn't possible (e.g. running on own machine/single box).

## Requirements

- Windows, PowerShell 7 or Windows PowerShell 5.1
- `git`, plus whichever of `az`, `gh`, `cf` / `wrangler` you use
- Node.js (for the guard hook)

## Folder layout

The scripts assume your repos live under one Git root, split into roots such as `Work` and `Personal`, with customers as folders under `Work`:

```text
D:\Git\
  Work\
    Contoso\          <- .azcustomer.json / .cfcustomer.json here covers every repo below
      app-repo\
      infra-repo\     <- or put one here to override for a single repo
    Fabrikam\
  Personal\           <- a .cfcustomer.json here covers all personal repos
```

The defaults are `D:\Git` and `D:\Git\Work`. Override them per run with `-GitRoot` / `-WorkRoot`, or set them once:

```powershell
$env:CF_GIT_ROOT  = 'C:\src'
$env:AZ_WORK_ROOT = 'C:\src\Work'
```

All three scripts are safe to re-run. Re-running refreshes the hook and agent rule, keeps existing logins and tokens, and refuses to overwrite a folder's settings with different values unless you pass `-Force`.

After the first run, restart open terminals (including VS Code's) and start new Claude sessions so the hooks and rules load.

## 1. Azure

[new-az-customer.ps1](scripts/new-az-customer.ps1) does the following:

- writes `<folder>\.azcustomer.json` (name, tenant, subscription, optional resource group)
- gives the customer its own az login in `%USERPROFILE%\.azure-profiles\<name>\`
- opens a browser sign-in for that tenant, or reuses the login if it is still valid
- checks the subscription really belongs to that tenant

`-Path` is relative to the Work root.

```powershell
# Set up a customer
.\scripts\new-az-customer.ps1 -Path Contoso `
    -TenantId 00000000-0000-0000-0000-000000000000 `
    -SubscriptionId 11111111-1111-1111-1111-111111111111

# One repo pinned to a different subscription, sharing the customer's login
.\scripts\new-az-customer.ps1 -Path 'Contoso\landing-zones' -Name contoso `
    -TenantId <tenant-guid> -SubscriptionId <other-subscription-guid>

# Limit agent changes to one resource group
.\scripts\new-az-customer.ps1 -Path 'Fabrikam\web-poc' -Name fabrikam-poc `
    -TenantId <tenant-guid> -SubscriptionId <subscription-guid> -ResourceGroup rg-web-poc

# Sign in with a device code (no browser on this machine)
.\scripts\new-az-customer.ps1 -Path Northwind -TenantId <guid> -SubscriptionId <guid> -DeviceCode

# Login expired: re-run the same command, or force a fresh sign-in
.\scripts\new-az-customer.ps1 -Path Contoso -TenantId <guid> -SubscriptionId <guid> -Relogin
```

With `-ResourceGroup`, the script lists your role assignments after login. If your rights go beyond that resource group (for example Owner on the subscription), only the agent guard enforces the limit, not Azure. A service principal scoped to the resource group would make it a hard limit.

| Switch | Effect |
| --- | --- |
| `-Name <name>` | Profile name (default: folder name, lower case, hyphens) |
| `-ResourceGroup <rg>` | Default `az` to this group and limit agent changes to it |
| `-DeviceCode` | Sign in with a device code instead of a browser |
| `-Relogin` | Force a fresh sign-in |
| `-SkipLogin` | Write the settings now, sign in later |
| `-Force` | Replace a folder's existing settings |
| `-NoProfileInstall` | Don't add the hook to your PowerShell profile |
| `-NoAgentRule` | Don't write the Claude rule |

Inside a customer folder:

```powershell
cd D:\Git\Work\Contoso
# az: contoso (subscription 1111...)
az account show --query name -o tsv
terraform plan      # uses ARM_TENANT_ID / ARM_SUBSCRIPTION_ID
```

## 2. Cloudflare

[new-cf-customer.ps1](scripts/new-cf-customer.ps1) does the following:

- writes `<folder>\.cfcustomer.json` (name and account ID, no secrets)
- stores a read and a write API token in `%USERPROFILE%\.cloudflare-profiles\<name>\`, encrypted with Windows DPAPI (only your Windows user on this PC can decrypt them)
- checks each token is active and can see the account before saving anything

`-Path` is relative to the Git root, so include `Work\` or `Personal\`.

```powershell
# Set up an account (prompts for the read token, then the write token; input is hidden)
.\scripts\new-cf-customer.ps1 -Path 'Work\Contoso' -AccountId 0123456789abcdef0123456789abcdef

# Cover every personal repo with one account
.\scripts\new-cf-customer.ps1 -Path Personal -AccountId <32-hex>

# Pass tokens from a secret store instead of pasting them
.\scripts\new-cf-customer.ps1 -Path 'Work\Contoso' -AccountId <32-hex> `
    -ReadToken (Get-Secret contoso-cf-read) -WriteToken (Get-Secret contoso-cf-write)

# One token for both read and write (proofs of concept, API token limits)
.\scripts\new-cf-customer.ps1 -Path 'Work\Fabrikam\web-poc' -Name fabrikam-poc `
    -AccountId <32-hex> -SingleToken

# Another folder on the same account: reuses the stored token, no prompt
.\scripts\new-cf-customer.ps1 -Path 'Work\Fabrikam\web-poc-nfr' -Name fabrikam-poc `
    -AccountId <same 32-hex> -SingleToken

# Rotate tokens
.\scripts\new-cf-customer.ps1 -Path 'Work\Contoso' -AccountId <32-hex> -ResetTokens
```

Where the settings file goes:

- **On a customer folder:** covers every repo under it.
- **On a whole root:** for example `-Path Personal` covers every personal repo.
- **On one repo:** overrides the folder above it (nearest wins). It is added to that repo's `.git\info\exclude` so it is never committed.

| Switch | Effect |
| --- | --- |
| `-Name <name>` | Profile name (default: folder name) |
| `-SingleToken` | One token used as both read and write (no read-only protection) |
| `-ResetTokens` | Replace stored tokens |
| `-SkipAccountCheck` | Token must be active, but skip proving it can see the account (for narrowly scoped tokens; double-check the account ID) |
| `-SkipVerify` | Don't call the Cloudflare API at all |
| `-Force`, `-NoProfileInstall`, `-NoAgentRule` | As for Azure |

Inside a Cloudflare folder, in your own terminal, `cf`, `wrangler` and Terraform use `CLOUDFLARE_ACCOUNT_ID` and the read token by default:

```powershell
cd D:\Git\Work\Contoso\app-repo
# cf: contoso (account 0123..., read token)
wrangler whoami
wrangler tail

cfw wrangler deploy     # run one command with the write token
Use-CfToken Write       # stay on the write token until you leave the folder
Use-CfToken Read        # back to read
```

The prompt shows `[cf:WRITE]` in red while the write token is active.

## 3. GitHub

Two parts, both keyed on the root folder a repo sits in:

- **Git** (clone, push, pull) uses an SSH key and author per root, through `includeIf` in your global git config.
- **`gh`** (PRs, issues, releases, `gh api`) can't use SSH, and its active account is global. [setup-gh-identity.ps1](scripts/setup-gh-identity.ps1) sets `GH_TOKEN` per root so `gh` acts as the right account.

`setup-gh-identity.ps1` needs an `includeIf` entry per root, because it stores the GitHub login as `github.user` in that root's config file. The SSH key and author in the same file are optional, but without them git pushes as whichever key SSH offers first, which may be a different account from `gh`.

### Per-folder git identity and SSH key (optional)

```text
~\.gitconfig                  only includeIf rules, one per root
  |-- D:/Git/Work/*      -> D:\Git\.gitconfig-work      -> ~/.ssh/id_ed25519_work
  '-- D:/Git/Personal/*  -> D:\Git\.gitconfig-personal  -> ~/.ssh/id_ed25519_personal
```

Skip any step you already have. Replace `<name>` with the root's label (for example `work`) and `<email>` with that account's email.

1. Generate a key for the root, and set a passphrase when prompted:

   ```powershell
   ssh-keygen -t ed25519 -C "<email>" -f "$HOME\.ssh\id_ed25519_<name>"
   ```

   This writes the private key `id_ed25519_<name>` (never share or commit it) and the public key `id_ed25519_<name>.pub`.

2. Copy the public key:

   ```powershell
   Get-Content "$HOME\.ssh\id_ed25519_<name>.pub" | Set-Clipboard
   ```

3. Sign in to GitHub as **that account**, go to Settings > SSH and GPG keys > New SSH key, choose **Authentication Key**, paste and save. If the organisation uses SAML SSO, click **Configure SSO** next to the key and authorise it.

4. Test the key on its own:

   ```powershell
   ssh -i "$HOME\.ssh\id_ed25519_<name>" -o IdentitiesOnly=yes -T git@github.com
   # Hi <github-username>! You've successfully authenticated, ...
   ```

5. Create the root's config file, for example `D:\Git\.gitconfig-<name>`:

   ```ini
   [user]
       name = Your Name
       email = <email>
   [core]
       sshCommand = ssh -i ~/.ssh/id_ed25519_<name> -o IdentitiesOnly=yes
   ```

   Don't add `[github]` yourself; `setup-gh-identity.ps1` writes `github.user` here.

6. Add the rule to the **end** of `~\.gitconfig` (not the file from step 5):

   ```ini
   [includeIf "gitdir/i:D:/Git/<Name>/"]
       path = D:/Git/.gitconfig-<name>
   ```

   Use forward slashes and keep the trailing `/` (this folder and everything under it). `/i` makes the match case-insensitive.

7. Check it inside a repo under that root. Rules only apply inside a git repo, so these return nothing in a bare folder:

   ```powershell
   git config user.email                        # <email>
   git config --show-origin core.sshCommand     # the <name> key, from .gitconfig-<name>
   git ls-remote origin                         # reaches GitHub as the right account
   ```

If pushes go to the wrong account, or you see "Permission denied" or "Repository not found":

- Check `sshCommand` has `-o IdentitiesOnly=yes`. Without it, SSH may offer another key first and GitHub signs you in as that account.
- Check the remote is SSH (`git@github.com:...`), not HTTPS. HTTPS remotes ignore the SSH key. Switch with `git remote set-url origin git@github.com:<org>/<repo>.git`.
- A clone can use the wrong key, because the folder rule matches a repo that doesn't exist yet. Force the key for the clone; after that the rule takes over:

  ```powershell
  git -c core.sshCommand="ssh -i ~/.ssh/id_ed25519_<name> -o IdentitiesOnly=yes" clone git@github.com:<org>/<repo>.git
  ```

If you don't want per-folder SSH keys, the config file can hold just `[user]`, or nothing at all; the `includeIf` entry is all `setup-gh-identity.ps1` needs.

### `gh` account per root

Map each root to an account. This opens a browser sign-in if `gh` doesn't have that account yet:

```powershell
.\scripts\setup-gh-identity.ps1 -Root Work     -User jdoe-work
.\scripts\setup-gh-identity.ps1 -Root Personal -User octocat

# Enterprise managed user, and check it can reach the org (catches SSO problems)
.\scripts\setup-gh-identity.ps1 -Root Client -User jdoe_acme -Org acme-corp

# Status of every root, and refresh the hook and rule
.\scripts\setup-gh-identity.ps1
```

Sign in **as that account** in the browser. If the browser is already signed in to GitHub as someone else, open the link in a private window. Afterwards the script restores your previous active `gh` account.

The folder decides the account, not the repo's remote. A work repo cloned under `Personal` acts as your personal account.

## 4. Agents

Agent shells start with `-NoProfile`, so the folder hooks never run there. The scripts write rules to `%USERPROFILE%\.claude\rules\` telling agents to load credentials with a prefix in the same PowerShell command:

```powershell
. "$HOME\.azure-profiles\az-customer-hook.ps1"; Update-AzCustomerEnv; az group list -o table
. "$HOME\.cloudflare-profiles\cf-customer-hook.ps1"; Update-CfCustomerEnv; wrangler whoami
. "$HOME\.gh-identity\gh-identity-hook.ps1"; Update-GhIdentityEnv; gh pr list
```

Each prints a line (`az:` / `cf:` / `gh:`) naming the customer or account. No line means no customer there, and the agent should ask you. Worktrees outside the Git root (T3, Claude) map back to the repo they came from.

T3 Code's Claude threads load these rules and the guard. Its Codex, OpenCode and Cursor agents do not.

The files in [.claude/rules/](.claude/rules/) are samples of what the scripts generate. Your real copies are written to `%USERPROFILE%\.claude\rules\` with your own paths.

## 5. The guard

Cloud changes are meant to go through pipelines (Well in my opinion :D). [guard-cloud-writes.mjs](.claude/hooks/guard-cloud-writes.mjs) is a Claude Code `PreToolUse` hook that checks every shell command and file edit an agent makes. It only affects agents; anything you type in your own terminal runs as normal.

### Install

Copy both hook files to `%USERPROFILE%\.claude\hooks\`:

```powershell
New-Item -ItemType Directory -Force "$HOME\.claude\hooks" | Out-Null
Copy-Item .\.claude\hooks\guard-cloud-writes.mjs, .\.claude\hooks\local-apply-allowed.txt "$HOME\.claude\hooks\"
```

Then register it in `%USERPROFILE%\.claude\settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|PowerShell|Write|Edit|MultiEdit|NotebookEdit",
        "hooks": [
          {
            "type": "command",
            "command": "node \"C:/Users/<you>/.claude/hooks/guard-cloud-writes.mjs\"",
            "timeout": 10,
            "onFailure": "block"
          }
        ]
      }
    ]
  }
}
```

Test it by piping a fake tool call in:

```powershell
'{"tool_name":"Bash","tool_input":{"command":"terraform apply"},"cwd":"D:\\Git\\Work\\Contoso"}' |
    node "$HOME\.claude\hooks\guard-cloud-writes.mjs"
# {"hookSpecificOutput":{..."permissionDecision":"deny",...}}
```

### Rules

By default (folder not in the list):

| Decision | Commands |
| --- | --- |
| Block | `terraform` / `tofu` / `terragrunt` apply, destroy, import, taint, state changes |
| Block | `pulumi up` / `destroy` |
| Block | `cfw`, `Use-CfToken Write` |
| Block | `wrangler deploy` / `put` / `delete` / `create` / `secret` / `versions deploy` (except `--local`) |
| Block | `cf ... create` / `update` / `delete` / `purge` / `deploy` |
| Block | POST / PUT / PATCH / DELETE calls to `api.cloudflare.com` |
| Ask | `az` changes (create, delete, update, start/stop, assign, run-command, deployment and so on) |
| Ask | Az PowerShell `New-` / `Set-` / `Remove-Az*`, `az rest` writes, management API writes |
| Ask | `wrangler d1 execute` against the remote database |
| Allow | Reads: list, show, get, what-if, `terraform plan` / `validate`, `wrangler dev` / `tail`, `gh pr create`, `gh api` |

Always blocked, whatever the list says:

- `az login` / `logout`, `az account set`, `Connect-AzAccount`
- `gh auth login` / `logout` / `switch` / `refresh` / `token`
- `cf auth login` / `logout`, `wrangler login` / `logout`
- reading Cloudflare token files or `Get-CfCustomerToken`

Always ask, whatever the list says: agent edits to the folder list, the guard script, Claude `settings.json` files, `.azcustomer.json` or `.cfcustomer.json`. This stops an agent unlocking itself.

When the folder has a `resourceGroup` in `.azcustomer.json`:

- **Block:** `az` / Az PowerShell changes naming any other resource group
- **Block:** creating, changing or deleting resource groups
- **Ask:** changes that name no resource group (check they only touch the right one)
- Reading other resource groups is fine.

### The folder list

[local-apply-allowed.txt](.claude/hooks/local-apply-allowed.txt) takes one folder per line, and everything under it counts. Lines starting `#` are comments.

```text
D:\Git\Personal\SomeRepo
allow: D:\Git\Work\Fabrikam\web-poc
```

- **Ask mode** (plain path): the blocked Terraform and Cloudflare changes become approval prompts.
- **Allow mode** (`allow:` prefix): those changes run with no prompt, and so do `az` changes inside the folder's resource group. `az` changes naming no resource group still ask.

Logins, token reads, other resource groups and the guard's own files never relax. The most specific listed folder wins. Add folders yourself; agent edits always prompt.

The match uses the agent session's working directory, so open the session in the listed folder or below it. A session started in a parent folder or a T3 worktree won't match.

### If the guard breaks

With `"onFailure": "block"` it fails closed: if Node is missing or the script errors, agent tool calls are blocked. Open `/hooks` in Claude Code to disable it, or fix the script.

Guard prompts start with `[guard-cloud-writes]`. Any other approval prompt comes from Claude Code's own permission mode.

## Where things live

| Path | Contents |
| --- | --- |
| `<folder>\.azcustomer.json` | Azure customer settings (no secrets) |
| `<folder>\.cfcustomer.json` | Cloudflare account settings (no secrets) |
| `%USERPROFILE%\.azure-profiles\` | Per-customer az logins, az hook, trusted-folder list |
| `%USERPROFILE%\.cloudflare-profiles\` | DPAPI-encrypted tokens, cf hook, trusted-folder list |
| `%USERPROFILE%\.gh-identity\` | gh hook (tokens stay in gh's own keyring) |
| `<git root>\.gitconfig-<root>` | SSH key, author and `github.user` per root |
| `Documents\PowerShell\profile.ps1` | Loads the three hooks (also `WindowsPowerShell\`) |
| `%USERPROFILE%\.claude\rules\` | Generated agent rules |

The hooks only trust settings files the scripts wrote (path plus SHA-256 list), so a `.azcustomer.json` or `.cfcustomer.json` committed in someone else's repo is ignored with a warning. If you edit one by hand, re-run the script for that folder to trust it again.

## Security notes

- **Azure logins are your own interactive account with its full rights.** There is no read-only Azure credential; the guard and agent rules are what limit an agent. If you want to limit further, I'd suggest go with an App Reg method instead.
- **Cloudflare folders using `-SingleToken` have no read-only protection.** The guard is the only thing stopping an agent writing there.
- **The guard matches command text.** A change hidden in a script file or built at runtime can get past it. Treat it as a safety net, not a security boundary.
- **Tokens are DPAPI-encrypted per Windows user.** Anything running as you on the same PC (including agents) can decrypt them; the guard blocks the obvious ways, but it is not a sandbox.
- **SSH private keys stay in `%USERPROFILE%\.ssh\`.** Only upload the `.pub` file, use a passphrase on every key, and delete a lost or leaked key in GitHub straight away.
- **Keep profile folders inside your user profile.** The scripts warn if they are elsewhere, because those folders hold refresh tokens.
